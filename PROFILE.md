This document is the normative description of the binding. It exists so that a second
implementation can be written against *this text* rather than reverse-engineered from
`agent.py`. The fixture generator is written from this document and deliberately does not
import `agent.py`; the reference implementation is then tested against the fixtures. Where the
two disagree, that is a bug in one of them, and this document says which behavior is required.

The key words MUST, MUST NOT, SHOULD, and MAY are to be read as described in RFC 2119.

Changes that alter any byte a peer produces or verifies (canonical form, field names or order,
derivations, signatures) require a new binding URI (`#technocore-room-v2`). Clarifications and
additional fixtures increment the profile revision only.

## 1. Roles and scope

- The **serving agent** offers skills. It owns a mailbox room and the task records it writes.
- The **caller** delegates a task to a serving agent and verifies the results.
- **The service** is technocore.chat. It is an untrusted rendezvous: it stores rooms and notes,
  verifies room-message signatures, and reports the verified signer as `from`. It does not
  authenticate note writers (§5.3).

Neither side needs an inbound network endpoint. This binding replaces A2A's HTTP transport only;
task lifecycle, method names, roles, parts, and error details follow A2A v1.0.

Out of scope for v1: streaming, push notifications, `GetTask` as an RPC (task state is read
directly, §9), `ListTasks`, non-text input parts, file/URL parts, and multi-turn tasks.

## 2. Notation

`C(x)` is the canonical JSON serialization of value `x` (§3). `H(s)` is the lowercase hex SHA-256
of the UTF-8 encoding of string `s` (64 characters). `B64U(b)` is base64url of bytes `b` without
`=` padding. Object members are listed in the order they MUST be emitted.

## 3. Canonical JSON

Every signed, hashed, or derived value in this profile uses one serialization. It is the output of
Python's `json.dumps(x, separators=(",", ":"), ensure_ascii=True)`, specified here independently:

1. No whitespace between tokens.
2. Objects emit members **in the order given by this profile** for values a producer creates, and
   **in received order** when a verifier re-serializes a value it parsed. Keys are not sorted.
3. Strings are enclosed in `"`. The characters `"` and `\` are escaped as `\"` and `\\`. U+0008,
   U+000C, U+000A, U+000D, U+0009 are escaped as `\b`, `\f`, `\n`, `\r`, `\t`. Every other code
   point below U+0020 or above U+007E is escaped as `\uXXXX` with **lowercase** hex; code points
   above U+FFFF are escaped as a UTF-16 surrogate pair, each half as `\uXXXX`. `/` is not escaped.
   All other characters are emitted literally. The output is therefore pure ASCII.
4. Integers are emitted in decimal with no leading zeros, no `+`, no exponent, and no fraction.
   Signed records MUST NOT contain non-integer numbers.
5. `true`, `false`, `null` are emitted literally.

**Raw form rule.** A signed record as stored or transmitted (its *raw* string) MUST already be
canonical: a verifier MUST parse it, re-serialize it with rule 2's received order, and reject the
record unless the result is byte-identical to the raw string. This rejects whitespace variants
and duplicate member names, which JSON parsers resolve differently.

## 4. Identity and signatures

- An identity is an Ed25519 key, named by its `did:key`: `"did:key:z"` + base58btc(`0xed 0x01` ||
  32-byte public key). Only Ed25519 `did:key` values matching
  `^did:key:z6Mk[1-9A-HJ-NP-Za-km-z]{44}$` are valid.
- A record signature is `B64U(Ed25519-sign(C(record without "signature")))`. The signer appends
  `"signature"` as the record's **last** member. A verifier removes `"signature"`, re-serializes
  the remaining members in received order, and verifies against the expected DID's key.

## 5. Service primitives used

These are technocore.chat's own contracts, summarized for implementers; the service, not this
profile, defines them.

### 5.1 Signed room write

`POST {base}/r/{room}?format=json` with body
`{"did":DID,"sig":SIG,"nonce":NONCE,"text":TEXT}`, where `SIG = B64U(Ed25519-sign(UTF-8(room + "|"
+ nonce + "|" + text)))`. The response carries the assigned sequence number at `posted.seq`. Rooms
named `mb-…` accept signed writes only. `TEXT` is at most **4096** characters.

### 5.2 Room read

`GET {base}/r/{room}?since=N&wait=W&limit=200&format=json` returns `{"messages":[…],"last_seq":L}`.
Each message has `seq`, `text`, and — for signed writes — `from`, the DID the service verified.
At most 200 messages are returned per read; retention is bounded by the service.

### 5.3 Notes

`GET {base}/kv/{ns}/{key}` reads a note. A plain read prefixes the value with a line starting
`!! UNTRUSTED CONTENT` and a blank line; clients strip everything through the first blank line.
`GET {base}/kv/{ns}/{key}/set/{percent-encoded value}` writes one, with optional `?if={expected}`
(compare-and-set, `409` on mismatch) or `?if_absent=1`. Values are single-line and at most
**8192** characters. **Anyone can write any note.** CAS is concurrency control between honest
writers, never authorization; authority comes only from signatures (§9).

## 6. Discovery

### 6.1 AgentCard

The serving agent's card is an A2A v1.0 AgentCard hosted on the agent's own origin (or handed over
out of band) — never on technocore.chat. Its `supportedInterfaces` MUST contain:

```json
{"url":"{base}/r/{mailbox}","protocolBinding":"https://github.com/brkcinar/technocore-a2a#technocore-room-v1","protocolVersion":"1.0"}
```

and a top-level `technocoreTransport` object with `base`, `did`, and `mailbox`. A caller MUST pin
`technocoreTransport.did` from a card or DID note it trusts; knowing the mailbox alone is not
enough to verify anything (§10).

### 6.2 DID note (optional)

A serving agent MAY publish `"{DID} mailbox:{mailbox}"` at `/kv/did-{F[0:2]}/{F[2:16]}`, where
`F = H(DID)`. Callers MAY also try the legacy `/kv/did/{F[0:16]}`. A resolved mailbox MUST match
the mailbox pattern in §7.1 or be rejected.

## 7. Request delivery

### 7.1 Mailbox

The serving agent's mailbox is a room matching `^mb-p-[a-z0-9][a-z0-9_-]{0,42}$` (signed-only and
unguessable). Callers MUST NOT send to any other room shape.

### 7.2 Request frame

A request is one JSON-RPC 2.0 object, serialized with `C`, posted as the `text` of one signed
write to the mailbox:

```
{"jsonrpc":"2.0","id":ID,"method":METHOD,"params":PARAMS}
```

`ID` is a string or a non-boolean integer. Callers SHOULD use a fresh 32-hex random string.
The service-verified `from` of the message is the **caller DID** for everything that follows.

### 7.3 Reply room

Every response to a request goes to exactly one room:

```
R(callerDid, agentDid, id) = "mb-p-a2a-" + H(C({"callerDid":callerDid,"agentDid":agentDid,"requestId":id}))[0:32]
```

The caller includes it as `params.metadata.technocoreTransport.replyMailbox`. The serving agent
MUST compute `R` from the verified caller DID, its own DID, and the frame id, and MUST NOT reply
anywhere else; if the supplied value differs, it sends no reply at all. This prevents a request
from using the agent as a signed relay into another room.

Before posting the request, the caller MUST read the reply room's current `last_seq` and then wait
for messages after it, so that a fast reply is not missed. The caller MUST ignore reply-room
messages whose `from` is not the pinned agent DID or whose `id` differs.

### 7.4 Transport retry

A write that times out or returns 5xx is ambiguous. The sender SHOULD first read the target room
for a message from its own DID with byte-identical `text`, and treat it as delivered if present.
Otherwise it MAY retry with a fresh nonce and signature but the **same frame text** (same `id`,
same params). Receiver deduplication (§11) makes this safe.

## 8. Methods

### 8.1 Validation and silent drops

The serving agent processes each mailbox message in sequence order. It MUST silently ignore a
message whose `text` is not a JSON-RPC object with `"jsonrpc":"2.0"` and a valid `id`, or that
has no `method` member, and it never replies to a message without a valid verified `from`.
Otherwise it checks, in order, replying to `R` with the first error that applies:

| Condition | Code | Error detail |
|---|---|---|
| `method` not a string | -32600 | — |
| `params` not an object | -32602 | `BadRequest` field `params` |

These two replies go to `R` directly (the params cannot be inspected). From here on, the agent
also requires the supplied `replyMailbox` to equal `R` (§7.3) and sends nothing if it does not:

| Condition | Code | Error detail |
|---|---|---|
| `SendMessage`/`CancelTask` with `technocoreTransport.callerDid` present and ≠ verified `from` | -32602 | `BadRequest` field `metadata.technocoreTransport.callerDid` |
| unknown method (no reply if `callerDid` mismatches) | -32601 | — |

Typed details use A2A v1.0's JSON-RPC mapping: `error.data` is a one-element array holding either
`{"@type":"type.googleapis.com/google.rpc.ErrorInfo","reason":…,"domain":"a2a-protocol.org","metadata":{…}}`
or `{"@type":"type.googleapis.com/google.rpc.BadRequest","fieldViolations":[{"field":…,"description":…}]}`.

Implementations MUST accept the v1.0 method names below. They MAY additionally accept the v0.3
names `message/send` and `tasks/cancel`, the role `user`, a part `kind` of `text`, and transport
fields at the top level of `params` instead of under `metadata.technocoreTransport`; they MUST NOT
emit them.

### 8.2 `SendMessage`

Caller emits:

```json
{"message":{"messageId":"…","role":"ROLE_USER","parts":[{"text":"…","mediaType":"text/plain"}]},
 "configuration":{"acceptedOutputModes":["text/plain"],"returnImmediately":true},
 "metadata":{"technocoreTransport":{"skill":"…","replyMailbox":"…","callerDid":"…"}}}
```

Additional checks, in order:

| Condition | Code | Error detail |
|---|---|---|
| `message.messageId` not a string | -32602 | field `message.messageId` |
| `message.role` ≠ `ROLE_USER` | -32602 | field `message.role` |
| `message.parts` empty or not an array | -32602 | field `message.parts` |
| no text part | -32005 | `ErrorInfo` reason `CONTENT_TYPE_NOT_SUPPORTED`, metadata `{"supportedMediaType":"text/plain"}` |
| `technocoreTransport.skill` present and not a string | -32602 | field `metadata.technocoreTransport.skill` |
| same request key, different request hash (§11) | -32600 | — |
| active-task limit reached | -32600 | — |

The task input is the text parts joined with one space. On success the serving agent creates the
task (§9.3) and replies:

- with `returnImmediately: true`: the task in its current state (normally `SUBMITTED`) at once;
- otherwise: the task once it reaches a terminal state.

The result is `{"task":TASK}` where `TASK` is:

```json
{"id":"…","contextId":"{mailbox}","status":{"state":"…"},
 "metadata":{"technocoreTransport":{"stateRecord":{…the current signed task-state record, as an object…}}},
 "artifacts":[{"artifactId":"{taskId}-result","name":"result","parts":[{"data":{…},"mediaType":"application/json"}]}]}
```

`artifacts` is present only for `COMPLETED` and `FAILED`. The caller MUST verify `stateRecord`
(§10) by re-serializing it with `C` and treating that as the raw record; the `status` field is a
convenience and is not authoritative.

### 8.3 `CancelTask`

Params: `{"id":TASK_ID,"metadata":{"technocoreTransport":{"replyMailbox":…,"callerDid":…}}}`.

| Condition | Result |
|---|---|
| `id` not 32 lowercase hex | -32602, field `id` |
| task unknown, **or owned by a different DID** | -32001, `ErrorInfo` reason `TASK_NOT_FOUND` |
| task already `CANCELED` | success: the task (idempotent) |
| task `COMPLETED` or `FAILED` | -32002, `ErrorInfo` reason `TASK_NOT_CANCELABLE`, metadata includes `state` |
| task `SUBMITTED` or `WORKING` | write `CANCELED` (§9.3), signal the running skill, reply with the task |

Only the DID that created a task may cancel it. A non-owner receives `TASK_NOT_FOUND`, identical to
an unknown id, so cancellation cannot be used to probe for other callers' tasks.

## 9. Task records

### 9.1 Location

Task ids are 32 lowercase hex characters chosen at random by the serving agent. For task `T`:

- state note: namespace `a2a-task-{T[0:2]}`, key `T[2:32]`
- artifact note: namespace `a2a-artifact-{T[0:2]}`, key `T[2:32]`

### 9.2 Envelopes

Task-state record, members in this order:

| Member | Value |
|---|---|
| `kind` | `"task-state"` |
| `taskId` | `T` |
| `ownerDid` | the caller DID that created the task |
| `agentDid` | the serving agent's DID (the signer) |
| `state` | `TASK_STATE_SUBMITTED`, `_WORKING`, `_COMPLETED`, `_FAILED`, or `_CANCELED` |
| `revision` | integer, 0 for the first record, +1 per transition |
| `previousHash` | `""` at revision 0; otherwise `H(raw of the previous record)` |
| `previousRecord` | `null` at revision 0; otherwise the previous record, as an object |
| `artifactHash` | only on `COMPLETED`/`FAILED`: `H(raw artifact record)` |
| `signature` | §4 |

Because each record embeds its predecessor, any record carries its full verifiable history.

Task-artifact record, members in this order: `kind` (`"task-artifact"`), `taskId`, `ownerDid`,
`agentDid`, `artifact` (an object, skill-defined), `workingStateHash` (`H(raw WORKING record)` of
the execution that produced it), `signature`.

### 9.3 Transitions

| From | To | Write |
|---|---|---|
| (none) | `SUBMITTED` rev 0 | `if_absent=1` |
| `SUBMITTED` | `WORKING` | `if={raw SUBMITTED}` |
| `SUBMITTED` or `WORKING` | `CANCELED` | `if={raw current}` |
| `WORKING` | `COMPLETED` / `FAILED` | artifact note first, then state with `if={raw WORKING}` |

A failed CAS means another writer moved first: the writer MUST re-read and verify the note and
MUST NOT retry its own transition from a stale predecessor. The serving agent keeps a private
checkpoint `H(raw)` of the last record it wrote for each task and MUST refuse to act on a note that
does not match it; that is how an overwritten public note is detected rather than obeyed.

A terminal `COMPLETED`/`FAILED` record is **bound** to its artifact iff `artifactHash` equals
`H(raw artifact)` **and** the artifact's `workingStateHash` equals the terminal record's
`previousHash`. An unbound pair MUST be rejected.

If the skill's artifact record would exceed the 8192-character note cap, the serving agent MUST
NOT leave the task in `WORKING`: it writes a `FAILED` record bound to a substitute artifact
`{"skill":…,"ok":false,"error":"…","reason":"ARTIFACT_TOO_LARGE","limit":8192}`.

## 10. Verifying a record

Given a raw record, the expected `kind`, task id, agent DID, and owner DID, a verifier MUST reject
unless all of the following hold:

1. the raw string is canonical (§3, raw form rule) and parses to an object;
2. `signature` is a string, and `kind`, `taskId`, `ownerDid`, `agentDid` equal the expected values;
3. for `task-state`: `revision` is a non-negative integer; at revision 0, `previousHash` is `""`
   and `previousRecord` is `null`; otherwise `previousHash` is 64 lowercase hex and
   `previousRecord` is an object;
4. for `task-artifact`: `workingStateHash` is a string;
5. the signature verifies against the expected agent DID (§4).

A caller additionally keeps, per task, the highest accepted `(revision, H(raw))` and MUST reject:

- a lower revision than the checkpoint (rollback);
- the same revision with a different hash (fork);
- a change of `agentDid` or `ownerDid` for a known task;
- a higher revision whose embedded chain, walked back to the checkpoint, does not verify record by
  record (each predecessor verified as in steps 1–5, with `revision` exactly one lower and
  `H(C(predecessor))` equal to the successor's `previousHash`), or does not end at the
  checkpoint's hash. With no checkpoint, the chain MUST verify back to revision 0.

A rejected record MUST NOT change the checkpoint.

## 11. Idempotency

- **Request key:** `H(C({"callerDid":callerDid,"requestId":id}))`. Two callers can use the same id
  without colliding.
- **Request hash:** `H(C(params))`, over the params as received.
- Before creating any task note, the serving agent MUST durably bind request key → (task id,
  request hash). A later frame with the same key and hash returns the existing task and MUST NOT
  run the skill again; the same key with a different hash is rejected (§8.2).
- The binding is bounded. The reference implementation keeps the newest **1024** bindings; once a
  binding is evicted, a replay of that id creates a new task. Callers MUST NOT rely on idempotency
  beyond that window.
- The reference implementation limits non-terminal tasks to **64** per serving agent.

## 12. Mailbox cursor and recovery

The serving agent persists the sequence number of the last mailbox message it handled (its
cursor). After a read from cursor `c` it MUST treat the following as an **uncertain gap** and
stop without advancing the cursor:

- the first returned message has `seq > c + 1` (messages were evicted or are beyond the window);
- no messages are returned but `last_seq > c`;
- `last_seq < c` (the room was reaped and recreated; its sequence restarted).

Resuming past an uncertain gap requires an explicit operator action (`recover-cursor --skip-lost`
in the reference implementation) with the serving process stopped. The skipped range is reported
and is **not** claimed to contain no requests. A request lost this way is never executed; its
caller observes a timeout and MAY resend with a new id.

A failure while handling one message (other than the gap conditions) does not stop the poller: the
cursor advances past that message, and the durable binding of §11 lets the caller's retry of the
same frame recover the same task.

## 13. Delivery guarantees

| Situation | Guarantee |
|---|---|
| Replay of a bound request (lost response, transport retry, serving-agent restart) | the skill runs at most once; the replay returns the same task |
| Restart after the binding but before `SUBMITTED` was written | the replay creates the task and completes it, once |
| Process death while a task is `WORKING` | **at-most-once, not recovery**: a replay returns the task in `WORKING` and the skill is not re-run; the task stays `WORKING` until an operator intervenes. Deployments that need recovery of abandoned work must add a lease/reconciliation policy; v1 does not define one |
| Uncertain mailbox gap | fail closed; explicit, reported, lossy skip (§12) |
| Request evicted from the ledger (§11) | no idempotency |
| Someone overwrites a public task note | detected and refused by both sides (§9.3, §10); the task can be denied service but not forged |

## 14. Limits and unsupported capabilities

| Limit | Value | Enforced |
|---|---|---|
| request/response frame | 4096 characters | sender MUST refuse to send a larger frame. A caller's oversize request creates nothing durable. A serving agent's oversize response (a terminal task with a large inline artifact) is not delivered, so callers SHOULD use `returnImmediately: true` and read the records directly (§9), as the reference caller does |
| note (state or artifact record) | 8192 characters | see §9.3 for oversize artifacts |
| room read window | 200 messages | §12 |
| ledger / active tasks | 1024 / 64 | §11 |

Non-text parts are rejected with `CONTENT_TYPE_NOT_SUPPORTED` before any task is created. There is
no chunking. URL or file references inside task text are untrusted data: a serving agent MUST NOT
fetch them as part of the binding, and nothing in v1 defines integrity binding for referenced
content.

## 15. Conformance

An implementation conforms to v1 when it reproduces every value in
`conformance/fixtures/v1/valid.json`, rejects every case in `invalid-records.json`, gives the stated
outcome for every sequence in `caller-checkpoints.json`, and meets the outcomes in
[CONFORMANCE.md](CONFORMANCE.md). The fixture identities use **published, deliberately insecure**
seeds; never use them for a real agent.
